## 요구사항별 구현

1. **전용 REVIEW_SUMMARY 경로:** `routing.ts`·`review-summary.ts`의 보수적 라우팅은 `세럼 추천`, 여러 상품 리뷰 **비교**, 명시적 리뷰 **정렬**과 특정 **단일 상품 리뷰 요약**을 분리한다. `graph.ts`의 `review_summary`는 예산/용도 인터뷰, 새 추천 후보 검색, RAG Retrieval, 개인화 Ranking을 실행하지 않는다. 모델이 임의 SQL/Commerce 액션을 실행하지 않는다.
2. **상품명 및 대화 문맥으로 대상 식별:** 이름이 있으면 기존 `catalog.searchProducts`로 후보를 찾고 Commerce `getProduct`로 정확한 ID를 재검증한다. 후보가 여럿이거나 불명확하면 **하나만 질문**, 임의 상품을 고르지 않는다. `2번 상품 리뷰`는 **해당 계정이 소유한 서버 Checkpoint에서 이전에 실제 표시했던 productId**에 한하여 처리한다. 조회 전에 Commerce 상세 재검증; 임의 클라이언트 ID/모델 생성 ID를 받지 않는다. `이 제품 후기에서 단점만`은 선택된 제품만 유지한다.
3. **Commerce 원본 리뷰:** `runtime.ts`가 기존 `getReviews(product_id,limit:20,sort:LATEST)`를 직접 사용한다. 별점·원본 리뷰 ID·상품 ID·옵션 ID·출처·본문 형식 검증 및 리뷰 ID 중복/출처 충돌 방지. 확인한 일부 표본(최대 20개)만 기술하며 `total_matching`을 긍정·부정 언급 수로 오용하지 않는다. **재고·예산 필터로 리뷰 조회를 차단하지 않는다.** 품절 상태의 활성 상품도 조회 가능하다. 현재 목록 검색은 Commerce의 `active=true` 스코프를 그대로 사용하므로 비활성/삭제 상품을 이름만으로 찾아내는 기능은 별도 구현하지 않았다.
4. **정확한 장단점 근거:** 제공된 LLM은 **Tool 없이** 서버가 조회한 리뷰 원문만 보고 `PRO/CON/MIXED`와 정확한 인용문을 제한된 JSON으로 제안한다. 서버는 원본 리뷰 ID에 존재하는 인용문인지, 중복·길이·출처·별점 방향을 검증한 뒤 인용하며 근거가 없으면 임의 장단점을 생성하지 않는다. 모델 장애/타임아웃에서는 별점이 함께 표시된 실제 리뷰 **인용문**만 제공하며 해당 인용을 검증된 긍정/부정 주장처럼 확대하지 않는다. 외부 링크, 연락처, 프롬프트 인젝션/명령·비밀정보 의심 본문은 모델 입력과 화면 인용에서 제외한다.
5. **표시 및 이력 보존:** 추천 1·2·3순위 카드 대신 `REVIEW_SUMMARY` 응답과 전용 근거 UI를 제공하고, 리뷰 ID·옵션 단위 출처가 유지된 접이식 근거 보기로 구분한다. `api.ts`, `runtime.readBrainHistory`가 `review_summary` 데이터를 반환한다. 데이터셋 변경 시 `currentDatasetResult`가 오래된 리뷰 근거/선택을 폐기한다. 기존 Memory 저장/확인/삭제, cart/checkout, 일반 추천은 변경하지 않았다.

## 명확한 범위와 알려진 한계

- 리뷰 요약은 최근/조회 가능한 **최대 20개** 표본의 의견으로 제한된다. 전체 후기 비율, 인기 장단점 정량 순위, 의학적 성능 등을 입증한다고 주장하지 않는다.
- 장단점·혼합 의견은 LLM 분류가 정확 인용·상품·원본 리뷰 ID·평점 방향과 맞는 경우에만 사용한다. **실제 한국어 정서 분류 의미 정확도**(복합 부정, 반어, 여러 성질의 평가)를 연결된 Claude로 별도 평가해야 한다. 안전한 fallback의 기본 기능은 출처 있는 원문 제시이며, 자동 의미 분류의 성공을 주장하지 않는다.
- 제품명 식별은 기존 활성 Commerce 검색 범위에서 처리한다. **품절(active=true, stock=0)**은 리뷰 조회 대상이다. 비활성 상품의 이름 검색은 기존 카탈로그 계약상 제공되지 않으며 실사용 요구가 있으면 별도 논의가 필요하다.
- `이 제품`은 이전 서버 표시 또는 선택 문맥이 유일할 때만 해석한다. 현재 쇼핑 상세 페이지를 별도의 client context로 모델에 넘기는 기능은 이번 QA10 범위에 넣지 않았다. 식별 못 하면 질문한다.
- REVIEW_SUMMARY와 REVIEW_COMPARE를 구분하되, 기존 응답 생성 권한·보안 장치는 그대로 보존한다.
